# 채팅 병목 분석·개선 전체 요약 — 2026-09-14

## 한눈에 보기

이번 작업은 로컬 단일 Spring Boot 프로세스에서 PostgreSQL·Redis를 사용하고, 10개 STOMP 클라이언트가 100건/s로 30초 동안 3,000개 메시지를 보내는 조건을 중심으로 진행했다. 원시 JSON·JSONL과 측정 도구는 측정 브랜치 `perf/chat-outbound-session-authorization`의 `5528d74` 시점에 보존하고 운영용 브랜치에는 포함하지 않는다.

작업 흐름은 세 단계다.

1. 전송·커밋·수신 ID와 STOMP queue, DB 트랜잭션, PostgreSQL 차단 관계를 계측했다.
2. `meetings` 행 쓰기 잠금을 `chat_room_sequences`의 방별 순번 행으로 옮기고 잠금 구간을 줄였다.
3. 구독자별 outbound Redis·DB 권한 재검증을 로컬 세션/구독 권한과 30초 TTL 재검증으로 줄였다.

## 결과 흐름

### 1. executor 1개에서 선행 queue 병목 확인

| 조건 | E2E p95 | inbound queue p95 | outbound queue p95 |
|---|---:|---:|---:|
| 집중, worker 1 | 99.78초 | 74.25초 | 75.03초 |
| 분산, worker 1 | 102.58초 | 77.81초 | 77.98초 |

worker를 4개로 늘린 대조 실험에서는 E2E p95가 집중 21.08초, 분산 17.09초로 감소했고, 그때 집중 조건의 meeting 행 잠금 대기가 더 크게 드러났다. worker 증설만으로 문제를 해결했다고 보지 않고 다음 병목을 관측하기 위한 실험으로 사용했다.

### 2. 순번 잠금 범위 축소

독립 3회 결과의 p95 중앙값은 다음과 같다.

| 조건 | 변경 전 E2E p95 | 변경 후 E2E p95 | 변경 후 순번 잠금 p95 |
|---|---:|---:|---:|
| 한 방 집중 | 21.08초 | 2.31초 | 11.02ms |
| 10개 방 분산 | 17.09초 | 396.62ms | 1.23ms |

집중 조건에서는 세 회차 합계 1,680개 잠금 표본 중 657개에서 차단 관계가 포함됐고, 분산 조건 1,597개 표본에서는 차단이 없었다. 따라서 잠금 범위는 줄었지만 동일 방 순번 행의 직렬화는 남아 있다.

### 3. outbound 권한 재검증 축소

순번 개선 후 분산 조건에서 구독자만 10명에서 1명으로 줄이자 E2E p95가 1.40초에서 31.58ms로, local fan-out p95가 29.19ms에서 1.63ms로 감소했다. 이를 근거로 구독자마다 실행되던 Redis 세션 확인과 DB 방 접근 확인을 개선했다.

분산·구독자 10명 개선 후 유효 3회 결과는 다음과 같다.

| 회차 | E2E p95 | inbound queue p95 | local fan-out p95 | outbound auth p95 | 외부 재검증 횟수 |
|---:|---:|---:|---:|---:|---:|
| 1 | 139.25ms | 92.98ms | 0.405ms | 0.006ms | 100 |
| 2 | 19.81ms | 0.052ms | 0.307ms | 0.005ms | 100 |
| 3 | 127.85ms | 87.44ms | 0.495ms | 0.006ms | 100 |
| 중앙값 | 127.85ms | 87.44ms | 0.405ms | 0.006ms | 100 |

개선 전 단일 clean 대조 실행과 비교하면 분산·구독자 10명 E2E p95는 `1.40초 → 127.85ms`, local fan-out p95는 `29.19ms → 0.405ms`, outbound auth p95는 `2.87ms → 0.006ms`였다. 3,000개 메시지를 10명에게 전달한 30,000번의 outbound 검사 중 Redis·DB 재검증은 회차별 100번이었다. 개선 전 값은 단일 회차이고 개선 후는 3회 중앙값이므로 운영 성능이나 안정 처리량으로 일반화하지 않는다.

구독자 1명 대조에서는 개선 전 E2E p95 31.58ms, 개선 후 3회 중앙값 29.38ms로 변화가 작았다. 이는 구독자 수에 비례해 반복되던 outbound 비용을 줄였다는 해석을 지지한다.

### 4. 남은 동일 방 병목

outbound 개선 후 집중·구독자 10명 E2E p95는 3회 `1.02초`, `2.01초`, `2.02초`로 중앙값 2.01초였다. 최신 세분화 실행은 다음과 같다.

| 구간 | p95 |
|---|---:|
| E2E | 2.134초 |
| inbound queue | 2.096초 |
| 순번 잠금 조회 | 72.867ms |
| 잠금 획득→커밋 | 13.165ms |
| 잠금 획득→서비스 반환 | 7.510ms |
| 서비스 반환→커밋 | 5.685ms |

100건/s는 평균 10ms마다 한 메시지가 들어오고 동일 방 순번 행은 p95 약 13ms 동안 잠겨 있다. 잠금 대기가 inbound worker와 Hikari 연결을 점유하면서 이후 요청이 executor queue에서 기다리는 연쇄 적체가 남는다.

## 보존한 계약

- `clientMessageId` 재시도와 중복 방지
- `(meeting_id, room_sequence)` 및 `(meeting_id, sender_id, client_message_id)` 유일성
- `roomSequence`/`afterSequence` 기반 정렬과 복구
- 메시지·읽음 상태·Outbox의 한 트랜잭션 커밋
- DB 커밋 이후 Redis/STOMP 전달
- 로그아웃·회원 탈퇴·참여 취소·권한 변경 시 WebSocket 세션 무효화
- JWT 만료 즉시 차단과 30초 TTL 만료 시 Redis·DB 재검증

## 검증 경계

- 유효 부하 실행은 모두 예정량·시도량·DB 저장량·관측 수신량이 각각 3,000건이고 미전송·미저장·저장 후 미수신·STOMP 오류·중복 수신은 0건이었다.
- 실제 FCM 및 push/email/image consumer는 비활성화했다. Outbox 저장 경로는 유지했다.
- 로컬 단일 서버 결과이며 AWS staging/운영 성능을 측정한 값이 아니다.
- `repository` 호출 시간에는 커넥션 획득과 SQL 실행이 함께 포함되므로 PostgreSQL 차단 표본과 같이 해석했다.
- 동일 방의 지속적인 100 msg/s는 여전히 순번 행 직렬화 한계가 있다. Kafka/Redis Streams 전환은 구현·운영 복잡도 때문에 이번 범위에서 적용하지 않았다.
